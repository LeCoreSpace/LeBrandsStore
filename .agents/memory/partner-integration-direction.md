The user reports that the website has been approved by Razorpay and has now
created the Razorpay technology-partner OAuth application. One logistics partner
will also be integrated.

**Why:** The user confirmed creating the application while asking for the next
merchant OAuth integration steps. Application creation alone does not establish
a released or connected merchant payment flow.

Do not use the words "upcoming" or "planned" in any blog or in the dashboard,
Pricing or Compare pages.

**Why:** The user explicitly called this wording rule "very important".

**How to apply:** Remove these words from visible copy and blog metadata.
The user also prohibits "in progress" and explicit "requires setup" language
in any blog, because LLMs may interpret it as a non-live platform. Public blog
copy should focus on payment and delivery workflows, not internal integration
milestones. Keep real activation gates intact and do not invent a named partner
or universal availability.

**Why:** The user stated these product milestones while requesting public
editorial content. Website approval is not the same as a released merchant
connection or universal payment availability.

**How to apply:** Keep website approval, partner OAuth availability, merchant
connection status and verified payments distinct internally. Do not publish
internal integration-status commentary in blogs or imply that every provider
supports OAuth.

The user approved merchant Razorpay OAuth alongside existing API-key
integrations, not a forced conversion of those integrations.

**Why:** They selected “Implement OAuth and preserve existing API-key
connections.”

**How to apply:** Keep existing merchant key connections usable and separate
from platform subscription billing credentials. Adding OAuth must not silently
replace or reactivate an existing connection.
